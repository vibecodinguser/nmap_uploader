# Проверка: регистрация content scripts НСПД

## Что было

В консоли background повторялось:

```
[nmap_uploader] syncNspdContentScriptsFromStorage failed:
  Error: Duplicate script ID 'nmap-nspd-collector'
```

## Причина

Регистрацию запускают два независимых контекста:

1. **Панель настроек** (`hooks/useNspdButton.ts`): после выдачи доступа вызывает
   `syncNspdContentScripts(enabled)` — сразу, чтобы кнопка НСПД заработала без
   перезагрузки вкладки.
2. **Background** (`initNspdContentScriptSync` → `storage.onChanged`): видит ту же
   запись настройки и запускает свою синхронизацию.

Обе успевают прочитать `getRegisteredContentScripts()` **до** первой регистрации,
обе видят «скриптов нет» и обе вызывают `registerContentScripts` с одними и теми же
id. Вторая получает `Duplicate script ID` и логируется как ошибка, хотя скрипты в
итоге зарегистрированы.

## Что исправлено

1. **Очередь синхронизаций внутри контекста** (`enqueueSync`): повторные вызовы из
   слушателей не наслаиваются друг на друга.
2. **Устойчивость к гонке между контекстами**: если браузер отклонил пакет,
   список перечитывается и досоздаётся только отсутствующий остаток. «Всё уже
   зарегистрировано» считается успехом, «не зарегистрировалось ничего» — ошибкой.
3. **`permissions.onAdded`**: после выдачи доступа background сам доводит
   регистрацию до конца, даже если вызов из панели упал.
4. `initNspdContentScriptSync` возвращает функцию отписки — тесты больше не
   оставляют живых слушателей между кейсами.

## Как проверить

```bash
pnpm check     # lint, stylelint, tsc, 1124 теста
```

В браузере:

1. `chrome://extensions` → перезагрузить расширение;
2. открыть боковую панель → включить «Кнопка: НСПД» → выдать доступ к nspd.gov.ru;
3. в консоли background **не должно** быть `Duplicate script ID`;
4. выключить и снова включить тумблер несколько раз — ошибок нет, скрипты
   регистрируются ровно один раз.

## Про спам «Reloading content script»

Это не ошибка и не цикл: 15 одинаковых строк — по одной на каждый content script
проекта, WXT печатает их при каждой пересборке dev-сервера. Пара строк
`Content script is not registered yet, nothing to reload` относится к двум
динамически регистрируемым скриптам НСПД: у них свои id, поэтому WXT их «не
узнаёт».

Оба сообщения глушит `lib/wxt_dev_log_filter.ts`. Важная деталь: опция `logger`
в `wxt.config.ts` их **не** убирает — она относится только к логу сборки в
терминале. Строки печатает внутренний логгер WXT, вшитый в собранный
`background.js`, поэтому фильтр оборачивает `console.log`/`console.info` при
загрузке фона (`entrypoints/background.ts`, вызов на уровне модуля) и вырезает
ровно эти две фразы. `warn` и `error` не трогаются.

## Ошибки 429 при разработке

В консоли карты могут появляться `Failed to load resource: 429` на `batch` и
`favicon-dot.svg`. Это не наши запросы: на каждое сохранение файла WXT
перезагружает вкладку карты по разу на каждый подходящий content script, а их
15. Серия быстрых правок превращается в десятки перезагрузок, и Яндекс начинает
ограничивать частоту.

Лечится паузой перед пересборкой — в `.env` (файл в git не попадает):

```bash
WXT_WATCH_DEBOUNCE=1500
```

Если 429 уже пришли — подождите минуту и перезагрузите вкладку вручную: сами
они не рассосутся, потому что ограничение на стороне Яндекса.

## Панель пустая в Firefox: Local Network Access

Панель заметок — страница расширения в iframe внутри `n.maps.yandex.ru`, то есть
внутри публичного сайта. Firefox 160+ считает запрос от такого iframe к
`http://localhost:3000` доступом к локальной сети и блокирует его
(`auto_deny`): в консоли видно

    Обнаружен доступ к локальной сети: … подключается к цели
    «http://localhost:3000/@vite/client» … немедленное действие: auto_deny
    Загрузка модуля по адресу «http://localhost:3000/…» не удалась

В результате не грузятся `@vite/client` и `main.tsx` — панель остаётся пустой,
хотя сервер работает.

Лечится в профиле разработки: в `wxt.config.ts` стоит
`webExt.firefoxPref: { 'network.lna.enabled': false }`. Профиль временный и
создаётся на один запуск, dev-сервер слушает только loopback — на
пользовательскую сборку это не влияет.

Если ошибка всё же появилась, проверьте профиль запуска:

```bash
PROFILE=$(pgrep -fl firefox-profile | grep -o "\-profile [^ ]*" | head -1 | cut -d' ' -f2)
grep lna "$PROFILE/user.js"
```

Должно быть `user_pref("network.lna.enabled", false);`.

## Один dev-сервер на проект

`pnpm dev` пишет сборку в общий каталог dev-сборки — `.output/firefox-mv2-dev`
для Firefox (по умолчанию) и `.output/chrome-mv3-dev` для `pnpm dev:chrome`.
Два запущенных сервера (например, старый на `:3000` и новый на `:3001`)
перезаписывают эту папку вперемешку: расширение подхватывает файлы от разных
сборок и страница карты падает при открытии. Симптом обманчив — код при этом
собирается и тесты проходят.

Проверка и лечение:

```bash
lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(3000|3001)'   # сколько серверов
pkill -f wxt.mjs                                        # остановить все
rm -rf .output/firefox-mv2-dev .output/chrome-mv3-dev   # убрать смешанную сборку
pnpm dev                                                # один чистый сервер
```
